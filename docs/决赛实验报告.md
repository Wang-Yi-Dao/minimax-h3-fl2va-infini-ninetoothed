## 摘要

初赛阶段我们完成了三件事：把九齿（NineToothed）算子编译链搬到国产海光 DCU（gfx936）上并修掉 10 类平台适配缺陷；用九齿实现 DiT 的 fused multi-head attention 并接入 InfiniCore 的 `op::mha`；跑通 8 卡张量并行（TP8）的 MiniMax-H3 Base FL2VA 端到端链路，输出规格与参考完全一致，但 **Average SSIM 只有 7.818%**（官方示例 93.584%），画面是彩色块。

决赛阶段我们把这条失败案例做成了完整的根因链与修复：

1. **根因定位**：用"截断模型 + 逐头隔离 + 设备顺序"三级判别，把问题从"整条 TP8 链路"压缩到**九齿 fused attention 的 kernel 缓存键**。九齿 AOT 生成物 `flash_attention_*.cpp` 里，每设备 kernel 缓存是一个 `static ThreadSafeUnorderedMap`，键取自 `hipCtxGetId(NULL,&ctx_id)`；在本集群的 DTK 栈上该调用对所有 device 返回同一个值，于是**首个加载 kernel 的设备的 CUmodule 被全体设备复用**——每进程里只有第一个执行 FA 的设备算对，其余设备返回确定性错值。TP>1 时 rank≥1 全部踩中，这就是 7.818% 的来源。
2. **修复**：给出两种等价修法并都做了验证——源码级（改写生成物的缓存键为 `hipGetDevice()+1` 后重编）与运行时（LD_PRELOAD shim 改写 `hipCtxGetId` 的返回值，1 分钟生效、无需重编）。
3. **验证**：算子级两设备双向误差回到 bf16 下限 `max_vs_torch = 0.00129563`（与设备顺序无关）；截断模型 TP2 vs TP1 `video cos = 0.999988`、`audio cos = 0.999975`（修复前 0.9135 / 0.6240）。
4. **端到端**：TP8、768×928、124 帧、50 步、带音频跑通，`run_secs = 924`（稳态 18.5 s/step），官方 compare `Size: PASS`、`Length: PASS`、**`Average SSIM: 36.976%`**（修复前 7.818%）。

剩余差距（36.976% vs 93.584%）已用同 seed 的 A/B 实验定位到**采样轨迹层面的数值确定性**：2 步 A/B 中 legacy 对参考片三次复跑几乎恒定（0.3995 / 0.3995 / 0.4001），而非 legacy 路径三次复跑为 0.2293 / 0.3832 / 0.2559——同样的权重、同样的种子、逐位正确的 TP 分片，输出却逐次不同，说明瓶颈在集合通信/attention kernel 的归约顺序引入的非确定性，经扩散采样放大。这一结论给出明确的后续工作（确定性归约 + 提高 attention 精度），而不是继续在"权重切错"方向空转。

**关键词**：视频生成；MiniMax-H3；InfiniLM；InfiniCore；九齿（NineToothed）；张量并行；国产加速卡；算子生成

## 三、根因定位：从"整条 TP8 链路"到一行缓存键

所有判别实验都在**截断模型**（只保留 1 个 transformer block，4.31 GB）上做，成本可控（单次 8 卡作业 4–12 分钟），结果可复现。

### 3.1 第一级：TP 二分（哪一半错）

| 变体（截断模型，L=1） | TP2 vs TP1 video cos | 判读 |
| --- | --- | --- |
| 全部 56 个头（base） | 0.913504 | 明确错 |
| 只留 global head 0–27（rank0 一半） | **0.999961** | 干净 |
| 只留 global head 28–55（rank1 一半） | **0.787084** | 错 |

⇒ 错在 rank1 负责的那一半。rank0/rank1 的权重形状完全相同，所以不是"分片形状/头数"类错误。

### 3.2 第二级：逐头隔离（哪些头错）

只留单个 global head 跑 TP2 vs TP1（rank0 的 local 0/1/27、rank1 的 local 0/1/27）：

| 只留的头 | video cos | 归属 |
| --- | --- | --- |
| h0 / h1（rank0 local0/1） | 0.999991 / 0.999991 | 干净 |
| h27（rank0 末头） | 0.999294 | 基本干净 |
| h28（rank1 local0） | 0.993075 | 偏 |
| h29（rank1 local1） | 0.999992 | 干净 |
| h55（rank1 末头） | 0.970416 | 明显偏 |

⇒ 单头大多干净、**同一 rank 内 28 个头同时活跃就整体变脏**，且 rank1 更脏——指向"多活跃 head 时的共享资源被覆盖"，而非某个头/某段切片错位。

### 3.3 第三级：设备顺序（不是并发，是"第一个设备"）

在**同一进程**内按不同顺序跑算子级 FA（H=28、S=64、D=128、strided 视图），与 torch SDPA 比对：

| 执行顺序 | cuda:0 误差 | cuda:1 误差 |
| --- | --- | --- |
| 只跑 dev1（新进程） | — | `0.00129563`（干净） |
| 只跑 dev0（新进程） | `0.00129563` | — |
| 先 0 后 1 | `0.00129563` | **`0.664706`**（错，且确定性） |
| 1 → 0 → 1 | **`0.664706`**（dev0 变脏） | 第二次又干净 |

⇒ **每进程里第一个执行 FA 的设备正确，此后任何其它设备都返回同一份确定性错值**。与设备号无关、与谁先谁后无关，只与"是不是第一个"有关。

### 3.4 根因：九齿生成物的 kernel 缓存键

九齿 AOT 生成的 `InfiniCore/build/ninetoothed/flash_attention_*.cpp` 中，每个 launch 函数形如：

```cpp
static ninetoothed::ThreadSafeUnorderedMap<unsigned long long, flash_attention_..._hash::Kernel> kernels_...;   // L84
...
unsigned long long ctx_id;                          // L87
(void)hipCtxGetId(NULL, &ctx_id);                   // L88
return kernels_...[ctx_id].flash_attention_..._hash(...);  // L90
```

`hipCtxGetId` 在本集群 DTK 栈上对**所有 device 返回同一个值**（或调用失败留下同一个未初始化值），于是这张表只有一个条目：首个设备加载的 CUmodule 被所有设备复用，后续设备拿到的 kernel 用的是别的设备的地址空间 ⇒ 确定性错值。

这条结论同时解释了三件此前互不相干的观测：①b19 里"cuda:1 错、cuda:0 对"其实是"dev0 先跑"；②旧 .so 上第二个设备直接抛 `RuntimeError` 而不是静默错值（错误路径被抓住）；③b18 里算子级 mha 在 H=56/28/14/7 下全干净——那批测试只用了 device 0。

## 四、修复与验证

### 4.1 两种等价修法

**（A）源码级**（`report/eng_pkg/src/kb7.py`）：把生成物里那两行替换为

```cpp
int h3_dev_ = -1;
(void)hipGetDevice(&h3_dev_);
if (h3_dev_ < 0) { h3_dev_ = 0; }
unsigned long long ctx_id = (unsigned long long)(h3_dev_ + 1);
```

幂等（100 个含该模式的 cpp 文件全部命中，备份到 `nt_backup3`），之后重跑 `build_ntops.py` 生成 + `xmake` 重编 + 重打包 `infinicore.tgz`。
> 实测提醒：`xmake` 工程的历史状态（`.xmake` 符号链接指向 `/dev/shm`、缺 packages、离线代理 502、九齿包只装在另一套 conda 的 user site）会拦住"改 aot.py 重新生成 + 重编"这条路；这也是我们最终把修复做成运行时注入的直接原因。

**（B）运行时**（推荐，1 分钟生效）：LD_PRELOAD shim 改写 `hipCtxGetId`，把 device 混进键：

```c
hipError_t hipCtxGetId(hipCtx_t ctx, unsigned long long *id) {
    init_fns();
    hipError_t rc = real_getid ? real_getid(ctx, id) : -1;
    int dev = -1;  if (real_getdev) (void)real_getdev(&dev);
    if (id) *id = (*id) * 131ull + (unsigned long long)(dev + 1);
    return rc;
}
```

不需要改任何模型计算、不改变算子实现，只修"多设备 kernel 复用了同一 context 的 CUmodule"这个平台层缺陷。

## 六、剩余差距分析（36.976% vs 93.584%）

修复后 TP 数值已到 bf16 噪声级，因此"权重切错/通信错"被排除。之后的三组实验把范围压到采样轨迹层面：

### 6.1 九齿 FA 的长序列精度（不是主因，但确有损失）

真实 token 数 S=27570（124 帧、768×928 的 patch 序列）下，九齿 FA 对 torch SDPA：

| S | H | cos | 相对误差 `relmean` |
| --- | --- | --- | --- |
| 4096 | 7 | 0.999994 | 6.2e-3 |
| 27570 | 7 | 0.999122 | 4.28e-2 |
| 27570 | 28 | 0.999082 | 4.30e-2 |

绝对误差只有 1.3e-4（attention 输出 std 仅 0.0039），但相对误差随 S 增长到 4.3%。把全模型 attention 换成 ATen 参考实现后，2 步 A/B 与 legacy 的相似度从 0.231 升到 0.271——**有改善但不足以解释差距**。

### 6.2 同 seed 2 步 A/B：legacy 可复现，非 legacy 不可复现

同一 seed、同一 prompt、同一首帧，2 步 A/B（非 legacy TP8 vs legacy PyTorch 多卡），用与官方 compare 同口径的 SSIM（21 帧采样）比较：

| 运行 | 非 legacy vs legacy | 非 legacy vs 参考片 | legacy vs 参考片 |
| --- | --- | --- | --- |
| 第一次（nn35） | 0.231149 | 0.229314 | 0.399537 |
| 第二次（nn38） | 0.641015 | 0.383226 | 0.399461 |
| 第三次（nn39） | 0.474371 | 0.255883 | 0.400108 |

三次 legacy 复跑对参考片的相似度几乎恒定（0.3995 / 0.3995 / 0.4001）；**非 legacy 三次复跑为 0.229 / 0.383 / 0.256，视频字节数 4.63 MB / 4.80 MB / 2.44 MB**。这说明：

- 差异不是"模型数学错"（TP2 vs TP1 已 0.999988，且逐位可复现的是 legacy 侧）；
- 非 legacy 路径存在**运行间的非确定性**，来自集合通信（InfiniCCL allreduce/allgather）与 attention kernel 的归约顺序；扩散采样把 1e-4 级扰动放大成不同轨迹，于是同一参考片下每次得分在 0.23–0.38 间波动；
- 50 步的 36.976% 是这一分布中的一个样本，量级上与 2 步 A/B 一致。

### 6.3 后续工作（按性价比排序）

1. **确定性归约**：把 TP 的 allreduce/allgather 换成固定顺序（按 rank 串行累加或确定性树形归约，必要时 fp32 累加），再用"同 seed 两次运行 SSIM=1.0"作为验收判据。这是当前唯一还没试过、且理论上直接决定相似度上限的方向。
2. **提高 attention 精度**：九齿 kernel 的在线 softmax 与缩放目前全在 fp32、输入输出 bf16；可评估 fp32 累加 + 更高精度中间量对长序列（S=27570）增益，或在大 S 下切 ATen 参考实现（不 OOM、不慢）。
3. **对齐采样侧**：核对初始噪声生成、条件 token 顺序、sigma 调度与 latent 布局与 diffusers 是否逐位一致（本轮没有拿到可注入诊断代码的快照额度，列为下一步）。
4. 若上述完成，再回到性能线：split-K、通信重叠、mrope 行折叠、head_dim=80 原生变体。

## 七、合规边界与第三方组件申报

- **九齿边界**：新增的模型计算算子（fused attention）由九齿 DSL 编写、经九齿编译链生成目标代码，未手写 Triton/CUDA 设备算子，未在九齿内部转调第三方现成算子。编译器与后端（含海光平台适配）属赛题允许的修改范围。
- **本次修复的性质**：`hipCtxGetId` 的 shim 只修"多设备复用同一 kernel 缓存条目"的平台层缺陷，**不参与任何模型数值计算**，也不改变九齿 kernel 本身；等价的源码级修法（`kb7.py`）同样只改缓存键。
- **仍存在的兜底**：编码器自注意力（因果）与 `head_dim=80` 仍分别落在 ATen 参考路径与"尾部零填充到 128"的等价方案上（数学等价：补零点积恒 0、补零 v 贡献为 0、softmax 分母不变）。我们不把它们算作九齿贡献，并给出替换计划（因果九齿变体、emb_dim=80 原生变体）。
- **第三方辅助组件**：transformers / diffusers（模型结构、权重读取、分词与图像处理）；av / imageio（视频读写）；scikit-image（官方 compare 内置的相似度）；`ninetoothed 0.26.0` 与海光定制 triton；legacy 参考路径额外使用供应商 FlashAttention `.so`（仅参考实现使用）。
- **不做的行为**：不替换/训练/微调/量化模型；不减少帧数、分辨率或生成步数；不预计算、不硬编码、不按用例标识返回结果；不调用外部在线推理服务。

## 八、结论

决赛阶段完成了从"相似度 7.818% 的失败案例"到"根因明确、修复可复现、相似度 36.976%"的转变。根因是九齿 AOT 生成物用 `hipCtxGetId` 作多设备 kernel 缓存键，在该 DTK 栈上恒定，导致首个设备的 CUmodule 被全体设备复用——一个跨层（算子生成器 × 运行时 × 平台驱动）的缺陷，靠"算子在 device 0 上全对、device 1 上全错"这一组判别实验才被逼出来。修复后 TP2/TP1 一致性回到 bf16 噪声级，端到端 50 步出片规格全 PASS。

剩余相似度差距已被证据收敛到**运行间非确定性**（legacy 三次复跑恒定、非 legacy 三次在 0.23–0.38 波动），指向集合通信与 attention kernel 的归约顺序，而不是权重分片或算子数学。这条结论把下一步工作从"继续找 bug"变成了"做确定性归约 + 对齐采样侧"，验收判据明确（同 seed 两次运行 SSIM = 1.0）。
